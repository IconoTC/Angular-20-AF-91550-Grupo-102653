## 📕Rutas anidadas

Podemos distinguir dos formas de organizar las rutas anidadas:

1. **Rutas anidadas independientes**, sin página padre: Se definen rutas hijas que no dependen de una ruta padre, es decir, cada ruta hija es una página independiente y no tiene una página padre que la contenga. 

```ts
{
  path: 'auth',
  children: [
    {
      path: 'login',
      loadComponent: () => import('./features/auth/pages/login-page'),
    },
    {
      path: 'register',
      loadComponent: () => import('./features/auth/pages/register-page'),
    },
  ],
},
```

Las rutas `auth/login` y `auth/register` son rutas hijas independientes, ya que no dependen de una página padre que las contenga. Cada ruta hija es una página independiente y no tiene una página padre que la contenga

2. **SubRutas de una página**: Se definen rutas hijas que se anidan bajo una ruta padre.

```ts
{
  path: 'auth',
  component: () => import('./features/auth/pages/auth-page'),
  children: [
    {
      path: 'login',
      loadComponent: () => import('./features/auth/pages/login-page'),
    },
    {
      path: 'register',
      loadComponent: () => import('./features/auth/pages/register-page'),
    },
  ],
},
```

Las rutas `auth/login` y `auth/register` son rutas hijas de la ruta padre `auth`, que tiene un componente (página) asociado. Esto significa que cuando se navega a una de las rutas hijas, el componente (página) de la ruta padre se renderiza incluyendo su propio router-outlet, que indica donde se renderizará el componente de la ruta hija.


En cualquiera de los caos, la carga de los componentes puede ser lazy, como se muestra en los ejemplos, usando `loadComponent` para cargar los componentes de las rutas hijas de forma diferida. O podría no serlo, cargando los componentes de las rutas hijas de forma inmediata, usando `component` en lugar de `loadComponent`.

## 🌐Páginas de la feature Auth

### Páginas

Creamos dentro de la feature 2 paginas alternativas de login y registro, que se renderizan en el mismo layout que las demás páginas, con el <h2> habitual y los estilos compartido de las demás páginas.

```shell
ng g c features/auth/pages/login-page --flat --project course-02
ng g c features/auth/pages/register-page --flat --project course-02
```

- Su única función es permitir la carga de los correspondientes componentes login y register
- Se crean como `pages` porque van a cargarse desde el router, y no como componentes que se renderizan dentro de otras páginas
- En consecuencia se exportan como `default` para que puedan cargarse de forma perezosa (lazy loading) desde el router
- No se crean en la raíz de la feature, `features/auth`, sino en la carpeta `pages` dentro de la feature, por su carácter de páginas anidadas
- No existe una página global a la feature, por lo que nuestras páginas se renderizan bajo el router-outlet de la app, y no bajo un router-outlet de la feature. 

#### Componentes

Para cada una de las páginas añadimos un componente inicial, en el que más adelante añadiremos el formulario.

```shell
ng g c features/auth/components/login-form --project course-02
ng g c features/auth/components/register-form --project course-02
```

Por el momento, se limitan a mostrar un párrafo

```ts 
template: `<p>login form</p>`,
template: `<p>register form</p>`,
```

### Rutas

En el router de la aplicación podríamos recoger estas páginas como rutas hijas de la ruta `auth`, que no tiene componente asociado, y que nos permite agrupar las rutas de login y registro bajo un mismo path.

```ts
{
  path: 'auth',
  children: [
    {
      path: 'login',
      loadComponent: () => import('./features/auth/pages/login-page'),
    },
    {
      path: 'register',
      loadComponent: () => import('./features/auth/pages/register-page'),
    },
  ],
},
```

En lugar de eso, nos llevamos las rutas hijas a un router específico de la feature, que nos permite agrupar las rutas de login y registro bajo un mismo path, y que se carga de forma perezosa (lazy loading) desde el router de la aplicación.

```ts auth.routes.ts
import { Routes } from '@angular/router';

export const authRoutes: Routes = [
  {
    path: 'login',
    title: 'Login | Course 02',

    loadComponent: () => import('../pages/login-page'),
  },
  {
    path: 'register',
    title: 'Register | Course 02',

    loadComponent: () => import('../pages/register-page'),
  },
];
```

El router principal de la aplicación se limita a cargar el router de la feature, que se encarga de cargar las rutas hijas de login y registro.

```ts app.routes.ts
import { authRoutes } from './features/auth/routes/auth.routes';

//...
{
  path: 'auth',
  children: authRoutes
},
```

## 📕Rutas con parámetros

En una ruta pueden indicarse parámetros, que pueden ser obligatorios u opcionales. Los parámetros obligatorios se indican con `:paramName`, mientras que los parámetros opcionales se indican con `:paramName?`. Por ejemplo:

```ts
{
  path: 'user/:id',
  loadComponent: () => import('./features/user/user-page'),
}
```

Cualquier url que incluya `user/` seguido de un valor, como `user/123`, `user/abc`, `user/xyz`, etc., navegará a la misma página, que podrá recoger el valor del parámetro `id` y renderizar el contenido correspondiente.

### Rutas con parámetros: uso de Observables

Tradicionalmente, para recoger el valor de los parámetros de la ruta se ha utilizado el servicio `ActivatedRoute`, que nos permite acceder a los parámetros de la ruta como observables de RxJS, y suscribirnos a los cambios en los mismos. 

El servicio `ActivatedRoute` también nos permite acceder a los parámetros de la ruta de forma síncrona, mediante la propiedad `params.snapshot`, pero no nos permite recibir los cambios en los parámetros cuando la ruta cambia, por lo que en este caso no es útil.

Volviendo al acceso reactivo a los parámetros existen varias opciones, como `params`, `paramMap`, `queryParams` y `queryParamMap`, que nos permiten acceder a los parámetros de la ruta y a los parámetros de consulta (query parameters) de forma reactiva, utilizando observables de RxJS.

La aproximación más propia de RxJs y más simple, sería no hacer privado el servicio y utilizar directamente el observable en la vista, utilizando el pipe `async` para suscribirnos al observable y obtener el valor del parámetro de la ruta.

```ts
export default class LoginPage {
  protected readonly #activatedRouter = inject(ActivatedRoute);

  // constructor() {}
}
``` 

```html
    @let formType = (activatedRouter.params | async)?.['formType'] || 'tdf'">

    @if (formType === 'tdf') {
      <alc-login-form-tdf />
    } @elseif (formType === 'mdf-rx') {
      <alc-login-form-mdf-rx />
    } @elseif (formType === 'signals') {
      <alc-login-form-signals />
    }
```

La directiva `@let` nos permite declarar una variable local en la vista, que se inicializa con el valor del observable `activatedRouter.params`, y que se actualiza automáticamente cuando el valor del observable cambia.

La gran ventaja de usar el pipe `async` es que no necesitamos suscribirnos al observable ni cancelar la suscripción cuando el componente se destruye, ya que Angular se encarga de ello automáticamente.

### Rutas con parámetros: interoperatividad de Observables a Signals

Usando el servicio `ActivatedRoute`, tanto con `params` como con `paramMap`, podemos acceder a los parámetros de la ruta, y suscribirnos a los cambios en los mismos, para actualizar el valor de la signal `formType` y renderizar el formulario correspondiente según el valor la signal.

```ts
type FormType = 'tdf' | 'mdf-rx' | 'signals';

export default class LoginPage {
  readonly #activatedRouter = inject(ActivatedRoute);
  readonly #destroyRef = inject(DestroyRef);
  protected readonly formType = signal<FormType>('tdf');

  constructor() {
    // this.#activatedRouter.paramMap
    this.#activatedRouter.params
      .pipe(takeUntilDestroyed(this.#destroyRef))
      .subscribe((params) => {
        this.formType.set(params['formType'] || 'tdf');
      });
  }
}
```

El operador de observables `takeUntilDestroyed` nos permite cancelar la suscripción cuando el componente se destruye, evitando posibles fugas de memoria. 

### Rutas con parámetros: uso de signals (forma actual)

Las versions más recientes de Angular permiten el uso de signals para acceder a los parámetros de la ruta, lo que nos permite simplificar aún más el código y evitar el uso de observables y suscripciones.



### Acceso a los parámetros desde LoginPage y RegisterPage usando signals

Recordemos que hemos configurado el provider `Router` con la opción `withComponentInputBinding()`, que nos permite acceder a los parámetros de la ruta desde cualquier componente de la aplicación, sin necesidad de pasar los parámetros como inputs.

En el componente solo necesitamos definir el parámetro como un input, y Angular se encargará de inyectar el valor del parámetro de la ruta en el componente.

```ts
type LoginFormType = 'tdf' | 'mdf-rx' | 'signals';

export default class LoginPage {
 protected readonly formType = input<LoginFormType>('tdf')
}

type RegisterFormType = 'monolithic' | 'custom-components';

export default class RegisterPage {
  protected readonly formType = input<RegisterFormType>('monolithic');
}
```

De esta forma no necesitamos inyectar el servicio ActivatedRoute y evitamos toda interacción con los elementos de RxJS.

En algunos casos es necesario añadir una función de transformación para validar el valor del parámetro y devolver un valor por defecto en caso de que el valor del parámetro no sea válido, como sucede con la '' (cadena vacía) que puede llegar desde una url sin parámetros.

```ts
type LoginFormType = 'tdf' | 'mdf-rx' | 'signals';

export default class LoginPage {
 protected readonly formType = input<LoginFormType, LoginFormType>('tdf', {
    transform: (value: string | null | undefined) => {
      if (value === 'tdf' || value === 'mdf-rx' || value === 'signals') {
        return value;
      }
      return 'tdf';
    },
  });
}
```

En nuestro caso no es necesario, ya que hemos definido una redirección de la ruta `login` a `login/tdf`, y de la ruta `register` a `register/monolithic`, que nos permite definir un valor por defecto para el parámetro `formType`, que se utiliza cuando no se especifica un valor en la url.

Podemos comprobar el funcionamiento de la renderización condicional accediendo a las rutas `login/tdf`, `login/mdf-rx` y `login/signals`, en el navegador y comprobando que se renderiza la vista correspondiente según el valor del parámetro `formType`.

Lo mismo hacemos en el caso del componente RegisterPage, que también tiene un parámetro de ruta `formType` que nos permite renderizar distintos formularios de registro según el valor del parámetro.

```ts
type RegisterFormType = 'monolithic' | 'custom-components';
```

De nuevo, podemos comprobar el funcionamiento de la renderización condicional accediendo a las rutas `register/monolithic` y `register/custom-components`, en el navegador y comprobando que se renderiza la vista correspondiente según el valor del parámetro `formType`.

#### Cierre del sidebar al navegar a otra página

Finalmente, en el sidebar, añadimos una opción extra, que pueda no incluirse en la demo durante el curso. Como la proyección es un menu, añadimos un efecto que nos permite cerrar el sidebar cuando se navega a otra página. 

Como la navegación se realiza a través del router de Angular, que utiliza observables de RxJs, podemos suscribirnos a los **eventos del router** y cerrar el sidebar cuando se produce un evento de navegación `NavigationStart`. Aplicamos el mismo patrón que en el caso de los parámetros de la ruta, utilizando el operador `takeUntilDestroyed` para cancelar la suscripción cuando el componente se destruye.

```ts
export class SideBar  {
 // Reactivity to navigation

  readonly destroyRef = inject(DestroyRef);
  readonly #router = inject(Router);

  constructor() {
    this.#router.events
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe((event) => {
        if (event instanceof NavigationStart) {
          this.isOpen.set(false);
        }
      });
  }
}
```

## 📕Rutas con estado

Como ya sabemos, el servicio `Router`, ademas de gestionar las rutas al ser instanciado con ellas, permite refinar determinadas operaciones relacionadas con las rutas

Al navegar a una ruta concreta (`navigate()` o `navigateByUrl()`) se puede acceder a su estado, capaz de almacenar información todo lo compleja que sea necesario

```ts
 this.#router.navigate(['/auth/login/tdf'], {
    state: { user: 'john_doe', role: 'admin', token: 'abc123' },
  });
```

Para acceder a este estado en el componente destino de la ruta, debemos inyectar el servicio `Router` y aprovechar dos de sus características: 

- es posible suscribirse a los eventos de navegación usando el método `events()`, que devuelve un observable. 

Estos eventos se desencadenan en las distintas etapas del ciclo de vida de la navegación 
  - `NavigationStart`, cuando se inicia la navegación y contiene la URL solicitada
  - `RoutesRecognized`, cuando el router determina qué ruta coincide con la URL y contiene la información del estado de la ruta
  - `GuardsCheckStart`, cuando comienza la fase de verificación de los guardias. El router evalúa los guardias de ruta como `canActivate` y `canDeactivate`
  - `GuardsCheckEnd`, cuando se completa la evaluación de los guardias y contiene el resultado (permitido/denegado)
  - `ResolveStart`, cuando comienza la fase de resolución de datos y los resolvers de la ruta comienzan a obtener datos
  - `ResolveEnd`, cuando se completa la resolución de datos y todos los datos requeridos
  - `NavigationEnd`, cuando la navegación se completa con éxito y el router actualiza la URL
  - `NavigationSkipped`, cuando el router omite la navegación (por ejemplo, si es la misma URL)
O en caso de error,
  - `NavigationCancel`, cuando el router cancela la navegación, a menudo debido a un guardia que devuelve false
  - `NavigationError`, cuando la navegación falla, por ejemplo, debido a rutas inválidas o errores de resolvers.

- desde la etapa `RoutesRecognized` es posible obtener información sobre el estado delas gracias al método `currentNavigation()`. Esta información deja de estar disponible una vez que se completa el proceso de navegación, por lo que es importante acceder a ella en el momento adecuado.

```ts
  readonly routerState = signal<NavigationState | null>(null);
  readonly #router = inject(Router);
  
  constructor() {
    this.#router.events
      .pipe(takeUntilDestroyed(this.destroyRef))
      .subscribe((event) => {
        if (event instanceof RoutesRecognized) {
          const navigation = this.#router.getCurrentNavigation();
          if (navigation && navigation.extras.state) {
            this.routerState.set(navigation.extras.state);
            console.log('Navigation state:', this.routerState());
          }
        }
      });
  }
```

## 📕Forms

Como hemos dicho, con LoginForm veremos ejemplos de los tres tipos de formularios que Angular nos permite crear:

- **Template-driven** forms: se definen en el template de la página, utilizando directivas de Angular para enlazar los campos del formulario con las propiedades del componente. Son más sencillos de implementar, pero menos flexibles y escalables.
- **Reactive forms o Model-driven forms**: se definen en el componente, utilizando la clase FormGroup y FormControl para crear un modelo de datos que representa el formulario. Son más flexibles y escalables, pero requieren más código y conocimientos de Angular.
- **Signal forms**: nuevos formularios basados en signals, también definidos en el componente

## Classic Forms: samples with LoginForm

### 📕Template driven forms

- Dependen de las directivas `ngForm` y `ngModel` incluidas en el módulo `FormsModule`, 
- la aplicación de la segunda de ellas da la primera de ellas da lugar a un objeto NgForm que representa el formulario y que nos permite acceder a sus propiedades y métodos, como `valid`, `invalid`, `pristine`, `dirty`, `value`, `resetForm()`, etc.
- el uso de la directiva `ngModel` nos permite enlazar el valor de un control del formulario con una propiedad del objeto NgForm, y el atributo `name`, nativo de HTML, nos permite definir el nombre del control dentro del formulario.
- el uso de la directiva `ngSubmit` nos permite ejecutar un método del componente cuando se envía el formulario, pasándole el objeto NgForm que representa el formulario, desactivándose por defecto el comportamiento nativo de envío del formulario, que recarga la página.
- la validación se define en el template del formulario, utilizando los atributos nativos de HTML5, como `required`, `minlength`, `maxlength`, `pattern`, `email`, etc.

El componente (modelo o controller) no es responsable de la creación y gestión del formulario; solo lo es de su lógica de negocio: el formato de los datos, y su envío al backend.  

Pese a todo esto, el objeto NgForm contiene a su vez un FormGroup, para representar el formulario, como los que veremos al hablar de los reactive forms. Por tanto la diferencia entre template-driven forms y reactive forms no es tanto la existencia de un modelo de datos que representa el formulario, sino la forma en que se crea y gestiona dicho modelo.

#### Submit y Navegación

El proceso de submit incluirá la llamada a un servicio, responsable del login de cara al backend. Si este aun no existe, el submit solo sera un console log para mostrar los datos que se enviarían al backend, y un reset del formulario para dejarlo limpio para un nuevo intento de login.

En el caso de que el servicio de login exista, se inyectará en el componente y se llamará a su método `login()`, pasándole los datos del formulario. Este método devolverá un observable que nos permitirá suscribirnos a su resultado, y navegar a la página de login, que cargará el componente de mostrar feedback al usuario tanto en caso de acierto como de error.

Si el formulario es inválido, se navegará a la misma página de login, pero con un estado que indique el error, para que el componente de feedback muestre el mensaje correspondiente. Esta situación trata de evitarse con los mecanismos de validación, pero se codifica por precaución, por si llegará a producirse.


```ts
export class LoginFormTdf {
  readonly #router = inject(Router);
  readonly #auth = inject(Auth);
  readonly #destroyRef = inject(DestroyRef);

  protected readonly isSending = signal(false);

  protected formSubmit(loginForm: NgForm) {
    if (loginForm.valid) {
      this.isSending.set(true);
      this.#auth
      .login(loginForm.value, {
        delayTime: 2000,
      })
      .pipe(takeUntilDestroyed(this.#destroyRef))
      .subscribe((state) => {
          // Navigate to the home page after successful login
          this.#router.navigate(['/auth', 'login', 'after-login'], {
            state,
          });
          loginForm.resetForm(); // Reset the form after submission
          this.isSending.set(false);
        });
    } else {
      // console.log('Form is invalid:', loginForm.value);
      this.#router.navigate(['/auth', 'login', 'after-login'], {
        state: {
          error: 'Form is invalid',
          token: '',
        },
      });
      loginForm.resetForm(); // Reset the form after submission
      this.isSending.set(false);
    }
  }
}
```

### 🧿LoginFormMdfRx: Model-driven Form (Rx)

### 📕Template driven forms

Los formularios reactivos se definen a nivel del componente, creando un objeto de la clase `FormGroup`. Sus propiedades son a su vez objetor de la clase `FormControl`, que representan los distintos controles del formulario

```ts
  public readonly formGroup = new FormGroup({
    email: new FormControl(''),
    password: new FormControl(''),
  });
```

Tanto el objeto `FormGroup` como los objetos `FormControl` permiten acceder las propiedades y métodos, del formulario t de cada control, como `value`, `valid`, `invalid`, `reset()`, etc.

Para la creación del FormGroup, Angular proporciona un servicio, `FormBuilder`, que implementa el patrón factory y en su método group devuelve una instancia de FormGroup, recibiendo como parámetro un objeto que implícitamente dará lugar a los FormControls que compondrán el FormGroup, asignándole a cada uno su valor inicial

```ts
  readonly #fb = inject(FormBuilder);
  public formGroup = this.#fb.group({
    email: [''],
    password: [''],
  });
```

Las validaciones se definen a nivel del componente, utilizando los validadores de Angular, como `Validators.required`, `Validators.minLength`, `Validators.maxLength`, `Validators.pattern`, etc. equivalentes a los atributos nativos de HTML5, como `required`, `minlength`, `maxlength`, `pattern`, etc.

```ts
  public formGroup = this.#fb.group({
    email: ['', [Validators.required, Validators.email]],
    password: ['', [Validators.required, Validators.minLength(6)]],
  });
```

Se pueden añadir **validadores personalizados**, que son funciones que reciben un control del formulario y devuelven un objeto con los errores de validación, o null si el control es válido.

```ts
  public formGroup = this.#fb.group({
    email: ['', [Validators.required, Validators.email]],
    password: ['', [Validators.required, Validators.minLength(6), this.customPasswordValidator]],
  });

  private customPasswordValidator(control: FormControl): ValidationErrors | null {
    const value = control.value;
    if (value && !/[A-Z]/.test(value)) {
      return { missingUpperCase: true };
    }
    return null;
  }
```

Igualmente, como tercer elemento del array que define cada formControl, podemos añadir **validadores asíncronos**, que es una función que recibe un control del formulario y devuelve un observable que emite un objeto con los errores de validación, o null si el control es válido.

```ts
  public formGroup = this.#fb.group({
    email: ['', [Validators.required, Validators.email], [this.asyncEmailValidator]],
    password: ['', [Validators.required, Validators.minLength(6)]],
  });

  private asyncEmailValidator(control: FormControl): Observable<ValidationErrors | null> {
    return of(control.value).pipe(
      delay(1000),
      map(value => {
        if (value === 'admin@example.com') {
          return { emailTaken: true };
        } 
        return null;
      })
    );
  }
```

Como vemos, la creación y gestión del modelo de datos que representa el formulario se realiza en el componente, y no en el template, como ocurría con los template-driven forms. Esto nos permite tener un mayor control sobre el formulario, y nos permite crear formularios más complejos y dinámicos.

En el template, utilizamos las directivas `formGroup` y `formControlName` para enlazar el formulario con el objeto `FormGroup` creado en el componente, y cada control del formulario con su correspondiente `FormControl`.

```html
  <form [formGroup]="formGroup" (ngSubmit)="onSubmit()">
    <label class="form-control" for="email">
      <span> Email </span>
      <input type="email" id="email" formControlName="email" />
    </label>
    ...
  </form>
```

Igual que en los template-driven forms, la directiva `ngSubmit` nos permite ejecutar un método del componente cuando se envía el formulario, sin que sea necesario pasarle valores, ya que el objeto `FormGroup` que representa el formulario es parte del componente, y podemos acceder a él directamente desde el método que maneja el envío del formulario.

```ts
  protected onSubmit() {
    if (this.formGroup.valid) {
      console.log('Form submitted:', this.formGroup.value);
      this.formGroup.reset(); // Reset the form after submission
    } else {
      console.log('Form is invalid');
    }
  }
```

#### Lógica en el componente

Por lo general, estas clases no se utilizan directamente, sino mediante el servicio `FormBuilder`, que nos permite crear los formularios de forma más sencilla y con menos código.

#### Submit y Navegación

El proceso de submit es prácticamente el mismo que en el formulario anterior: 

- establecemos el flag `isSending` a true para deshabilitar el botón de submit mientras se procesa la solicitud de login
- lanzamos la llamada a un servicio, responsable del login de cara al backend, pasándole `formaData`, obtenido a partir del valor del `formGroup`
- en la suscripción a la respuesta del servicio, navegamos a la página de login, que cargará el componente de mostrar feedback al usuario tanto en caso de acierto como de error
- añadimos un reset del formulario (ahora con el método `reset()` del FormGroup) para dejarlo limpio para un nuevo intento de login.

```ts
          error: 'Form is invalid',
          token: '',
        },

      this.isSending.set(false);
    }
```

```ts
    rememberMe: [false],
  });

  protected formSubmit() {
    if (this.loginForm.valid) {
      this.isSending.set(true);
      const formData: LoginRequest = this.loginForm.value;
      this.#auth
        .login(formData, {
          delayTime: 2000,
        })
        .pipe(takeUntilDestroyed(this.#destroyRef))
        .subscribe((state) => {
          // Navigate to the home page after successful login
          this.#router.navigate(['/auth', 'login', 'after-login'], {
            state,
          });
          this.loginForm.reset(); // Reset the form after submission
          this.isSending.set(false);
        });
    } else {
      // console.log('Form is invalid:', loginForm.value);
      this.#router.navigate(['/auth', 'login', 'after-login'], {
        state: {
          error: 'Form is invalid',
          token: '',
        },
      });
      this.loginForm.reset(); // Reset the form after submission
      this.isSending.set(false);
    }
  }
}
```

## 📕Signals Forms. Conceptos básicos

Los formularios basados en signals son una nueva forma de crear formularios disponible de forma estable en Angular 22, que nos permite definir el formulario y sus controles desde el componente (igual que en los formularios MD, basados en RxJs ), pero en este caso como signals, y utilizar la directiva `FormField` para enlazar el formulario con el template. Recientemente se ha añadido la directiva `FormRoot` para mejorar el proceso de submit.

En el componente se define

- el **modelo de datos** del formulario como un interface, que nos permite anotar el tipo del valor del formulario y sus controles
- un signal que representa el **estado del formulario**, con un valor inicial de todos los campos, generalmente a cadena vacía, o false en el caso del checkbox
- un objeto de tipo `FieldTree`, creado mor la función `form`, que representa una **vista reactiva** del formulario:
  - es una vista reactiva sobre el signal que representa el estado del formulario
  - se crea a partir de dicha signal
- el contenido de dicha signal es un objeto `FieldState` que representa el **estado del formulario**
  - el estado nos permite acceder a sus propiedades como `value()`, `valid()`, `invalid()`, `dirty()` o `touched` y métodos `reset()`, etc. Son equivalentes a las propiedades y métodos de `FormGroup` y `FormControl`, pero en este caso basados en signals, y por tanto reactivos. (En este caso no existen propiedades como `pristine` o `untouched`)
- como segundo parámetro de la función `form`, podemos pasar un callback que define el **schema del formulario**, con sus validaciones. Este callback recibe como parámetro el path del formulario, que nos permite acceder a los controles del formulario y definir sus validaciones.

Esto supone algunas diferencias importantes en la forma de entender los formularios, por lo que hay quien habla de un cambio de paradigma:

- Tu **modelo** es la fuente de la verdad y define el schema. 
- El formulario es una **vista reactiva** sobre ese Signal. 
- Los errores viven en el **schema**. Con tipado automático basado en el modelo. Fine grained gracias a los Signals.

## Formulario de login basado en signals

### 🧿LoginFormSignalsForm: Signal-based Form

Como primer ejemplo de formulario basado en signals básico, crearemos un formulario de login, con los mismos campos que los formularios anteriores, y con las mismas validaciones.

#### Lógica en el componente

En el componente crearemos un signal para representar el valor o estado del formulario, anotando su tipo de acuerdo al interface correspondiente y dándole un valor inicial de todos los campos a cadena vacía, o false en el caso del checkbox.

```ts
export interface LoginModel {
  email: string;
  password: string;
  rememberMe: boolean;
}


@Component({
  ...
})
export class LoginFormSignals {

  readonly #loginModelInitialState: LoginModel = {
    email: '',
    password: '',
    rememberMe: false,
  };

  // Signal representing the form model
  readonly #loginModel = signal<LoginModel>(this.#loginModelInitialState);

  protected readonly loginFieldTree = form(this.#loginModel)

  protected formSubmit() {
    const fieldTree: FieldTree<LoginModel> = this.loginFieldTree;
    const fieldState: FieldState<LoginModel> = fieldTree();
    const formValue = fieldState.value();

    const fieldEmail: FieldTree<LoginModel['email']> = fieldTree.email;
    const fieldStateEmail: FieldState<LoginModel['email']> = fieldEmail();
    const emailValue = fieldStateEmail.value();
    
    console.log('Form submitted', formValue);
    console.log('Email submitted', emailValue);
  }
}
```

La función `form()` nos devuelve un objeto de tipo `FieldTree`, que representa una **vista reactiva** del formulario. En el se incluye cada uno de los controles del formulario, que son objetos de tipo `FieldTree`.

Si usamos el getter del signal `loginFieldTree`, o de cualquiera de los `FieldTree` de los controles, podemos acceder al `FielState` del formulario, y a sus propiedades y métodos, como `value()`, `valid()`, `invalid()`, `reset()`, etc.

#### Vinculación al template

En el template se utilizan las directivas `FormField` y `FormRoot`, importadas de `@angular/forms/signals` para enlazar el formulario con el template. La segunda de ellas se ha añadido recientemente para mejorar el proceso de submit.

```ts
  imports: [FormRoot, FormField],
  template: `
    <form [formRoot]="loginFieldTree" (submit)="formSubmit()">
      <label class="form-control" for="email">
        <span> Email </span>
        <input type="email" id="email" [formField]="loginFieldTree.email" />
      </label>
      ...
    </form>
  `
```

En este caso, la directiva `formRoot` se aplica al elemento `form`, y la directiva `formField` se aplica a cada uno de los controles del formulario, enlazándolos no con un nombre, sino con las propiedades correspondientes del objeto `loginFieldTree`.

En lugar del evento `ngSubmit`, que no está disponible en los formularios signals, utilizamos el evento nativo `submit` del elemento form, que nos permite ejecutar un método del componente cuando se envía el formulario.

- si se ha usado la directiva `formRoot`, el evento `submit` se controla para que no tenga su valor por defecto, y no recargue la página
- si no se ha usado la directiva `formRoot`, el evento `submit` se comporta como un evento nativo, y para evitar la recarga la página se debe usar `preventDefault()` en el evento recibido en el controlador del submit.

Hay que tener en cuente que tampoco estarán disponibles las clases de CSS que Angular aplica a los formularios y controles, como `ng-valid`, `ng-invalid`, `ng-touched`, `ng-untouched`, etc. por lo que habrá que definir nuestras propias clases de CSS para mostrar el feedback de las validaciones o utilizar las propiedades del objeto `FieldState` de cada control para añadir estilos al feedback de las validaciones.

#### Valor del formulario

De nuevo, como herramienta en desarrollo, que luego eliminaremos, añadimos un \<pre> que nos permite ver el valor del formulario en tiempo real, utilizando el pipe `json` para mostrarlo en formato JSON.

```html
  <pre>{{ loginFieldTree().value() | json }}</pre>
```

En este caso accedemos al estado del formulario, es decir el valor de la signal `loginFieldTree` mediante la llamada a su getter `loginFieldTree()`, y al valor de la propiedad `value` mediante la llamada a su getter `value()`.

#### Validación y feedback

Igual que el los formularios MD, las validaciones se definen en el componente, en este caso en un callback que se pasa como segundo parámetro al método `form()` como **schema** de validación, Esta función recibe el valor del formulario y devuelve un objeto con los errores de validación.

```ts
export class LoginFormSignals {
  ...
  protected readonly loginFieldTree = form(this.#loginFormState, (path) => {
    required(path.email, { message: 'El email es obligatorio' });
    email(path.email, { message: 'El email debe ser una dirección de correo válida' });
    required(path.password, { message: 'La contraseña es obligatoria' });
    minLength(path.password, 6, { message: 'La contraseña debe tener al menos 6 caracteres' });
  });
  ...
}
```

El API de signals forms nos permite definir validaciones para cada uno de los campos del formulario, utilizando funciones como `required`, `minLength`, `maxLength`, `pattern`, `email`, etc. que reciben como primer parámetro el path del campo, y como segundo parámetro un objeto con las opciones de la validación, como el mensaje de error.

La función  que define el schema puede declararse aparte, como cualquier callback, y pasarse como referencia al método `form()`, para mantener el código más limpio y legible, dejando más claro el concepto de **schema de validación** como una propiedad del componente.

```ts
readonly #loginFormSchema = (path: any) => {
  required(path.email, { message: 'El email es obligatorio' });
  email(path.email, { message: 'El email debe ser una dirección de correo válida' });
  required(path.password, { message: 'La contraseña es obligatoria' });
  minLength(path.password, 6, { message: 'La contraseña debe tener al menos 6 caracteres' });
};

protected readonly loginFieldTree = form(this.#loginModel, this.#loginFormSchema);
```

A la hora de mostrar el feedback de las validaciones, podemos utilizar la propiedad `errors` del control representado en el objeto `loginFieldTree`. A diferencia de los formularios reactivos, `errors()` nos devuelve un array con el error de validación activo en el campos del formulario como item 0.

```ts
  @if (loginFieldTree.email()?.invalid() && loginFieldTree.email()?.touched()) {
    <p class="error">{{ loginFieldTree.email().errors()[0].message }}</p>
  }
``` 

Opcionalmente, en lugar acceder al error activo, podemos iterar el array de errores del campo del formulario, mostrando nuevamente el error de validación activo en el campo, utilizando un bucle `for` de Angular. 

```ts
  @if (loginFieldTree.email()?.invalid() && loginFieldTree.email()?.touched()) {
    <ul class="error">
      @for (error of loginFieldTree.email().errors(); track $index) {
        <li>{{ error.message }}</li>
      }
    </ul>
  }
```

También es posible acceder a todo el conjunto de errores del formulario, utilizando la propiedad `errorSummary` del objeto `loginFieldTree`, que nos devuelve un array con los errores de validación de cada uno de los campos del formulario.

```ts
<p>Errores del formulario</p>
<ul class="error">
  @for (error of loginFieldTree().errorSummary(); track $index) {
    <li>{{ error.message }}</li>
  }
</ul>
```

### 📕Submit API en los Signal Forms

Inicialmente este proceso hace uso de diversos elementos, nativos de HTML y de Angular.

- el evento `submit` del elemento form, al que se le asigna un manejador en el componente
- el atributo `novalidate` del elemento form, para evitar que el navegador realice la validación nativa de HTML5
- en el manejador se recibe el evento `submit` y se llama a `preventDefault()` para evitar que el navegador recargue la página
-  la función `submit()`, que recibe un objeto `FieldTree` que representa el formulario, junto con un callback asíncrono, que solo sera ejecutado si el formulario es válido. En el callback suele incluirse la llamada a un servicio que se encargue de enviar los datos del formulario al backend, que se resolverá con la respuesta acertada o con un error. 
- Los errores pueden integrarse en el propio `FieldTree` como `ValidationError` asociados a campos específicos del formulario, integrándose la validación del lado servidor con la validación del lado cliente, y mostrando el feedback de los errores en el template del formulario.
-  Si la función callback retorna errores, el proceso de submit se considera fallido, y el formulario queda en estado inválido, mostrando los errores devueltos por el backend. Si la función callback no retorna un valor (undefined), el proceso de submit se considera exitoso, y el formulario queda en estado válido, mostrando un feedback de éxito al usuario.
  
```ts
protected async submitForm(event: Event) {
  event.preventDefault();
  
  submit(this.loginFieldTree, async (fieldTree: FieldTree<LoginModel>) => {
    const fieldState: FieldState<LoginModel> = fieldTree();
    const formValue = fieldState.value();
    console.log('Form submitted', formValue)
    
    const result = await this.#auth.loginPromise(formValue);

    if (result.status === 'error') {
      // Handle server-side validation errors
      const serverErrors: ValidationError.WithOptionalField[] = []

      if (result.errors) {
        for (const error of result.errors) {
          serverErrors.push({
            field: error.field,
            kind: 'server',
            message: error.message,
          });
        }
      }
    } 
  }
}  
```

-  el estado submit del formulario, que se puede obtener mediante la propiedad `submitted()` del objeto `FieldTree`, y que nos permite mostrar un feedback al usuario de que el formulario se está enviando.
-  el método `reset()` del objeto `FieldTree`, que nos permite resetear el formulario a su estado inicial, pasando a false las propiedades `dirty()` y `touched()` de cada control del formulario, pero sin cambiar su valor inicial. Esto último sucede si en la llamada al método pasamos los valores iniciales, que son asignados al modelo del formulario, utilizando internamente su método `set`.

#### Directiva formRoot

En las últimas actualizaciones del API de Signals en Angular, se ha añadido la directiva `formRoot`, que nos permite simplificar el proceso de submit, evitando tener que utilizar el evento `submit` del elemento form, y el atributo `novalidate`, y evitando tener que llamar en el manejador del submit tanto a `preventDefault()` como a la función `submit()`.

Al usar esta directiva, la llamada a `submit()` se realiza internamente, y la lógica del submit se define como parte del propio formulario, añadiendo un  objeto de opciones al crear el objeto `FieldTree` del formulario, con la propiedad `submission`, que también es un objeto, con la propiedad `action` que recibe un callback que se ejecuta cuando el formulario es válido.

```ts
  protected readonly loginFieldTree = form(
    this.#loginModel, 
    this.#loginFormSchema, 
    { submission: { action: this.submitForm.bind(this) }}
    );
```

El valor de la propiedad `submission.action` es un callback asíncrono sera recibido por submit() y se ejecutara cuando el formulario es válido, recibiendo como parámetro el objeto `FieldTree` del formulario, que nos permite acceder a su estado y valor.

```ts
  protected submitForm(fieldTree: FieldTree<LoginModel>) {
    const fieldState: FieldState<LoginModel> = fieldTree();
    const formValue = fieldState.value();
    console.log('Form submitted', formValue);
    //...
  }
```

Si se usa como callback un método de la clase, hay que hacer un bind del método al objeto `this` de la clase, para que el callback tenga acceso a las propiedades y métodos de la clase.

Este método es asíncrono y puede manejar la llamada al servicio responsable del login, recibiendo una promesa con el resultado, para luego continuar gestionando los errores de servidor o con la navegación a la página de inicio, una vez finalizado el proceso de login.

Al iniciarse la llamada a la función `submission.action`, el estado del formulario pasa a `submitting() = true`, y al finalizar la ejecución de la función tras resolverse la promesa, el estado del formulario pasa a `submitting() = false`. Esto nos permite mostrar un feedback al usuario de que el formulario se está enviando.

#### Submit y Navegación

El proceso de submit incluirá la llamada a un servicio, responsable del login de cara al backend, pasándole los datos de la signal value(), que ya están tipados de acuerdo con el interface LoginForm. 

En nuestro caso no nos importa el resultado de la `submission.action`, ya que en cualquier caso finalizado el login, se navega a la página de login, utilizando el servicio `Router` de Angular para pasea en el state la información con los resultados del login.

Aun así, si queremos conservar la funcionalidad de que el estado del formulario pase a `submitting() = false` al finalizar la ejecución de la función, debemos hacer que la función devuelva una promesa que se resuelva con un valor void, para que el submit() interno de la directiva `formRoot` pueda finalizar correctamente.

Nuestro servicio de login ya dispone de una función `loginPromise()` que devuelve una promesa, utilizando la función `firstValueFrom()` de RxJs, por lo que podemos hacer un `await` de la llamada a dicha función, y devolver un valor void al finalizar la ejecución de la función. Si no existe esa función en el servicio, la conversión mediante `firstValueFrom()` puede hacerse en el componente.

Una vez resuelta la promesa del método del servicio, podemos navegar incorporando su resultado a la ruta y resetear el formulario, tanto su estado como su valor, para dejarlo limpio para un nuevo intento de login.

```ts
  protected readonly loginFieldTree = form(this.#loginModel, this.#loginFormSchema, {
    submission: {
      action: this.submitForm.bind(this),
    },
  });

 protected async submitForm(loginFieldTree: FieldTree<LoginModel>) {
    const formData = loginFieldTree().value();
    const state = await this.#auth.loginPromise(formData);
    // Reset the form after submission
    loginFieldTree().reset(this.#loginModelInitialState);
    // Navigate to the home page after successful login
    this.#router.navigate(['/auth', 'login', 'after-login'], {
      state,
    });
  }
```
En la creación de formData podríamos añadir las transformaciones y validaciones que fueran necesarias.

Otra alternativa es que el propio `submission.action`, que también es un callback asíncrono, devuelva una promesa von valor distinto de void. En ese caso Angular entiende que es un error, y el estado del formulario pasa a `submitting() = false`, pero el formulario queda en estado inválido, mostrando los errores devueltos por el backend. Si la función callback no retorna un valor (undefined), el proceso de submit se considera exitoso, y el formulario queda en estado válido, mostrando un feedback de éxito al usuario.

#### 👁️‍🗨️Test del componente LoginFormSignals

Nuevamente, como la estrategia de los tests de los formularios anteriores ha sido en todo momento la de caja negra, es decir testar el comportamiento del componente sin entrar en su implementación, los tests de este componente son similares a los de los componentes anterior, con una diferencia en un selector y sobre todo, un cambio respecto al uso del servicio, que ahora corresponde a un nuevo método, basado en promesas.

Para acceder a los errores de un control concreto usaremos `form .error` en lugar de `.error`, ya que fuera del formulario se han añadido los errores sumarios, usando también para ellos la clase `error`. 

Eliminamos el caso de uso `it('should NOT submit a INVALID form', ...)` ya que el submit de un formulario inválido no se ejecuta, y por tanto no hay que testarlo.

El método del servicio del que se crea un mock esta ahora basado en promesas:

```ts
providers: [
  {
    provide: Auth,
    useValue: {
      loginPromise: vi.fn().mockResolvedValue({}),
    },
  },
],
```

Al testar el submit, hay que tener en cuenta su asincronía, y por tanto el test debe ser asíncrono, y no es suficiente con hacer un `await` de la llamada a `fixture.whenStable()` para esperar a que se resuelva la promesa devuelta por el método del servicio.

En este caso, para esperar a que se resuelva la promesa devuelta por el método del servicio, podemos hacer un `await` de la llamada a `vi.runAllTicks()`, o utilizar `vi.waitFor` que nos permite esperar a que se cumpla una condición, en este caso que el método del servicio haya sido llamado.

## 📕Custom Controls

Angular define una serie de interfaces para **componentes personalizados**, `FormValueControl` y  `FormCheckboxControl`, que nos permiten crear componentes personalizados que se integren con el sistema de formularios de Angular. Cuando el componente implementa una de estas interfaces, nos permitan utilizar la directiva `FormField` para enlazar automáticamente el control personalizado con el estado, la validación y el enlace de datos del formulario.

Estos componentes se encargan de renderizar el control nativo de HTML. Externamente, reciben como input el `FieldTree` del control que representa el input o checkbox. 

Internamente utilizan obligatoriamente una `modelSignal`, para enlazar el valor del control con el valor del `FieldState`, y para actualizar el estado del control cuando cambia su valor.

```ts
readonly value = model.required<T>(); // bind to fieldState.value()
```

Ademas, el interface permite definir como inputs muchas de las propiedades del control, como `disabled`, `required`, `readonly`, `touched`, `invalid`, `errors` etc, que se enlazan automáticamente con los valores correspondientes del estado del control (fieldState).

```ts
readonly disabled = input.required<boolean>();
readonly required = input.required<boolean>();
readonly touched = model.required<boolean>();
readonly invalid = input.required<boolean>();
readonly errors = input.required<readonly ValidationError[]>();
```

Opcionalmente, se podrían usar estos valores y mostrar los errores de validación si los hay en función de los estados touched e invalid.

Otras alternativa es que un componente independiente se ocupe de mostrar los errores de validación, y que se pueda reutilizar en cualquier formulario y con cualquier control.

### 🧿Custom Input

En el contexto de los formularios basados en señales, los controles personalizados dependen directamente del `FieldTree`, que será gestionado por la directive `FormField`, lo que permitirá

- integrar fácilmente las validaciones del formulario y el feedback de los errores
- que se puedan utilizar en cualquier formulario basado en signals. 

Podemos crear un componente personalizado para los inputs de tipo texto, que reciba como inputs 

- el texto que debe mostrar (label) y 
- el `FieldTree` del control que representa el input
 
El componente se encargue de

- renderizar el input nativo de HTML y su label
- enlazar el estado del input con el valor del FieldState
- mostrar los errores de validación si los hay.

```ts
import { Component, input } from '@angular/core';
import { FieldState, FormField } from '@angular/forms/signals';

@Component({
  selector: 'alc-input',
   imports: [],
  template: `
    <label for="{{ id() }}" class="form-control">
      <input
        type="{{ type() }}"
        id="{{ id() }}"
        placeholder=" "
        [value]="value()"
        (input)="value.set($event.target.value)"
        (blur)="touched.set(true)"
      />
      <span>{{ label() }}</span>
    </label>
    @if (invalid() && touched()) {
      <p class="error">
        {{ errors()?.[0]?.message }}
      </p>
    }
  `,
  styles: ``,
})
export class Input {

  readonly value = model.required<string>();
  readonly errors = input([] as readonly ValidationError[]);
  readonly invalid: InputSignal<boolean> = input(false);
  readonly touched = model(false);


  readonly type = input<string>('text');
  readonly label = input.required<string>();
  readonly id = computed<string>(() => this.#generateId());
  
  #generateId() {
    return `${this.type()}-${Math.random().toString(36).slice(2, 9)}`;
  }
}
```

En la plantilla, el valor del placeholder se establece a un carácter espacio, para que el label se muestre correctamente cuando el input está vacío. El label se mueve hacia arriba cuando el input está enfocado o tiene valor, y vuelve a su posición original cuando el input está vacío y no está enfocado.

En el componente la modelSignal `value` se enlaza con el valor del FieldState del control, y se actualiza cuando el usuario escribe en el input. La propiedad `errors` se enlaza con los errores de validación del control, y la propiedad `invalid` se enlaza con el estado de validación del control.

La propiedad `touched` es un signalModel que se establece a true cuando el input pierde el foco, y que nos permite mostrar los errores de validación solo cuando el usuario ha interactuado con el control.

#### 👁️‍🗨️Alternativas en el Test del componente Input

El test de este componente presenta algunas particularidades:

- como en todos los componentes que definen inputs obligatorios, tenemos que proporcionárselos en los test, utilizando como ya hemos visto el método `setInput()` de `fixture.componentRef`.
- la función `form()` nos permite crear un objeto de tipo `FieldTree` a partir de un signal y un esquema de validación, pero no podemos utilizarla fuera de un contexto de inyección como el que proporciona un componente, o en nuestro caso, `TestBed` con su método `runInInjectionContext`.
- aunque tengamos un objeto de tipo `FieldTree`, no podemos pasarlo directamente al componente Input, ya que este no tiene un input de tipo `FieldTree`, que realmente existe en la directiva `FormField
- `FormField` no está dentro de Input: Angular la instancia sobre el elemento <alc-input> cuando compila el template del formulario, y le pasa como input el FieldTree del control correspondiente. 

Existen tres alternativas

- Para un test unitario puro de Input, usar TestBed.createComponent(Input) y probar solamente su API y DOM, sin esperar sincronización con FieldTree.
- Para probar la integración Input + FormField, se puede crear un HostComponent en el test, que utilice nuestro componente Input, y testarlo de la forma estándar.
- La creación programática del Input funciona sin host, y permite añadir la directiva `FormField` pero añade bastante infraestructura,  dejando de usar ComponentFixture.

### 🧿Custom CheckBox

Siguiendo el ejemplo anterior podemos crear un componente personalizado para los inputs de tipo checkbox. El componente 

- recibe como inputs el texto que debe mostrar (label) y el FieldTree del control que representa el checkbox, 
- implementa la interfaz `FormCheckboxControl` de Angular, que nos permite utilizar la directiva `FormField` para enlazar automáticamente el estado del checkbox con el valor del FieldTree, y de mostrar los errores de validación si los hay.
- expone un modelSignal `checked` que se enlaza con el valor del FieldState, y que se actualiza cuando el usuario interactúa con el checkbox.
- expone también los inputs `disabled`, `required`, `touched`, `invalid` y `errors`, que se enlazan automáticamente con los valores correspondientes del estado del control (fieldState).
- añadimos como opcional un input `id` para aportar el id del input, o creamos uno cuando no se suministra.   

```ts
import { Component, input } from '@angular/core';
import { FieldState, FormField } from '@angular/forms/signals';

@Component({
  selector: 'alc-check-box',
  imports: [],
  template: `
    <label for="{{ id() }}" class="custom-checkbox">
      <input type="checkbox" 
        [id]="id()" 
        [checked]="checked()" 
        (change)="checked.set(!checked())"   
        (blur)="touched.set(true)"/>
      <span class="check-mark"></span>
      <span class="label-text">{{ label() }}</span>
    </label>
    @if (invalid() && touched()) {
      <p class="error">
        {{ errors()?.[0]?.message }}
      </p>
    }
  `,
  styles: ``,
})
export class CheckBox implements FormCheckboxControl {
  readonly checked = model.required<boolean>();

  readonly errors = input([] as readonly ValidationError[]);
  readonly invalid = input(false);
  readonly touched = model(false);

  readonly label = input.required<string>();
  readonly id = input<string>(this.generateId());

  generateId() {
    return `checkbox-${Math.random().toString(36).slice(2, 9)}`;
  }
}
```

## 📕Controles de selección

En HTML, los controles de selección son aquellos que permiten al usuario seleccionar una opción de un conjunto de opciones, como los radio buttons y los select.

Con independencia del tipo de formulario que estemos utilizando, se pueden crear estos controles programáticamente a partir de un conjunto de datos, lo que facilita que se puedan actualizar dinámicamente los valores a elegir.

Esta información forma parte de lo que sse conoce como **datos maestros** (**master data**), y se puede definir en un archivo de constantes, o bien en un servicio que nos devuelva los datos desde el backend.

```ts
interface masterData {
  key: string;
  message: string;
};
```

A partir de este punto se pueden adoptar dos enfoques: 

- el modelo de datos del formulario guarda la clave del objeto seleccionado, y el control de selección devuelve la clave del objeto seleccionado, que luego se puede utilizar para buscar el objeto completo en el array de datos maestros

- el modelo de datos del formulario guarda el objeto completo seleccionado, y el control de selección devuelve el objeto completo seleccionado. En el caso de los formularios basados en signals, esto dificulta la forma en que trabajan los controles, ya que los radio buttons y los select devuelven el valor de la opción seleccionada, y no el objeto completo. 

## Signals Forms y controles de selección

Para tener un ejemplo algo más completo, añadimos un formulario de registro basado en signals, que incluye otros elementos, como radio buttons y select, y que nos permite ver cómo se comportan estos elementos en un formulario basado en signals.

El conjunto de controles iniciales del formulario será

```ts services/auth.ts
register(
  data: RegisterRequest,
  options: Partial<AuthOptions> = {},
): Observable<RegisterResponse> {
  const finalOptions = { ...DEFAULT_AUTH_OPTIONS, ...options };

  const hasError =
    !finalOptions.success || !data.email || !data.password || data.email.includes('error');

  const result = hasError
    ? {

      }

          gender: data.gender,
          hasCourse: data.hasCourse,
          course: data.course,
          isOk: data.isOk,
          registerDate: new Date(),
        },
      };

  return of(result).pipe(delay(options.delayTime as number));
}
```

####  Lógica en el componente

En primer lugar definimos el interface que representa el formulario, y un array de opciones para los radio buttons y el select.

```ts
interface RegisterForm {
  email: string;
  password: string;
  firstName: string;
  surname: string;
  gender: Gender;
  genderKey: Gender['key'];
  hasCourse: boolean;
  course: Course;
  isOk: boolean;
}
```

Para los valores objetos que representan  datos maestros (o master data)  incluimos la posibilidad de guardar el objeto completo, y también solo la clave del objeto, para poder enlazarlo con los radio buttons y el select, que solo devuelven el valor de la opción seleccionada.

Los pasos siguientes son ya conocidos, y son los mismos que en el caso del formulario de login basado en signals:

1. Definimos un objeto con los valores iniciales del formulario, con todos los campos a cadena vacía, o false en el caso del checkbox
2. Creamos un signal que representa el estado del formulario, con el valor inicial definido en el paso anterior
3. Creamos un objeto de tipo `FieldTree`, que representa una **vista reactiva** del formulario, a partir del signal que representa el estado del formulario.
4. Al crear el objeto `FieldTree`, podemos añadir  el **schema del formulario** con sus validaciones, como callback anónimo, o mejor a través de una propiedad de la clase. Cualquiera de ambos recibe como parámetro el path del formulario, que nos permite acceder a los controles del formulario y definir sus validaciones.
 
```ts
export class RegisterForm {
  readonly #initialValues: RegisterModel = {
    email: '',
    password: '',
    firstName: '',
    surname: '',
    gender: { key: '', message: '' },
    isOk: false,
    hasCourse: false,
    course: { key: '', message: '' },
  };

  protected readonly genders = signal(GENDERS);
  protected readonly courses = signal(COURSES);

  protected readonly user = signal<RegisterModel>(this.#initialValues);
  protected readonly registerForm: FieldTree<RegisterModel> = form(this.user, (schema) => {
    required(schema.email);
    email(schema.email);
    ...
  });

  submitForm() {
    console.log('Form submitted:', this.registerForm().value());
  }
}
```

#### Valor del formulario

En el `FieldState` obtenemos al valor de la propiedad `value` mediante la llamada a su getter `value()`.

#### Vinculación al template: problemas con objetos

En el caso de los radio buttons y los select, solo podemos obtener el valor de la opción seleccionada, y no el objeto completo, enlazando el control con la propiedad del formulario que contiene la clave del objeto (key), y no con la propiedad que contiene el objeto completo.

Para terminar utilizamos el evento `(change)` del control radio button, para actualizar el objeto completo, accediendo al value de FieldState del control radio button (`registerForm.gender()`), y haciendo set a la signal que almacena el valor con el objeto completo.


```html
<fieldset aria-label="Gender">
  <legend>Gender</legend>
  @for (item of genders(); track $index) {
    <label [for]="'gender-' + item.key" class="form-control checkbox">
      <input
        type="radio"
        [id]="'gender-' + item.key"
        [formField]="registerForm.gender.key"
        [value]="item.key"
        (change)="registerForm.gender().value.set(item)"
      />
      {{ item.message | titlecase }}
    </label>
  }
</fieldset>
```

En el select la respuesta al evento change es similar, pero en este caso accedemos al target del evento y debemos haces casting del tipo, por lo que pasamos el código a un método del componente.

```html
<label class="form-control" for="course">
  <span>Course</span>
  <select
    id="course"
    [formField]="registerForm.course.key"
    (change)="selectChange($event)"
  >
    @for (item of courses(); track $index) {
      <option [value]="item.key">{{ item.message }}</option>
    }
  </select>
```

En el handler del evento change, aprovechamos la propiedad `selectedIndex` del target del evento, nativa de HTML, que nos da el índice de la opción seleccionada, para obtener el objeto completo del array de opciones, que asignamos a la signal correspondiente.

```ts
protected selectChange(event: Event) {
  console.log('Select', this.registerForm.course())
  const index = (event.target as HTMLSelectElement).selectedIndex;
  const selectedOption = index >= 0 ? this.courses()[index] : { key: '', message: '' } as Course;
  this.registerForm.course().value.set(selectedOption);
}
```

#### Validación y feedback

Las validaciones se definen en el componente, y como buena práctica lo haremos en una propiedad de la clase, que es un callback que se pasa como segundo parámetro al método `form()` como **schema** de validación. Esta función recibe el path del formulario, que nos permite acceder a los controles del formulario y definir sus validaciones.

```ts
readonly #registerFormSchema = (path: any) => {
  required(path.email, { message: 'El email es obligatorio' });
  email(path.email, { message: 'El email no es válido' });
  required(path.password, { message: 'La contraseña es obligatoria' });
  minLength(path.password, 6, { message: 'La contraseña debe tener al menos 6 caracteres' });
  required(path.gender.key, { message: 'Indicar el género es obligatorio' });
  //....
};

protected readonly registerForm = form(this.user, this.#registerFormSchema);
```

El feedback al usuario se realiza en el template, comprobando si el control es inválido y ha sido tocado, y mostrando el primer mensaje de error del array de errores del control.

Sin embargo los casos en que el control es un objeto, como en el caso de gender, son un poco particulares, ya que

- la validación esta definida sobre la propiedad que contiene la clave del objeto, y no sobre la propiedad que contiene el objeto completo
- la propiedad `errors` del control que contiene el objeto completo estará vacía, ya que no tiene validaciones, 
- disponemos de la propiedad errorSummary, que almacena los errores de un nodo y de todo sus descendientes, donde SI encontraremos los errores de validación del control que contiene la clave del objeto.

```ts
@if (registerForm.gender()?.invalid() && registerForm.gender()?.touched()) {
  <p class="error">
    {{ registerForm.gender()?.errorSummary()?.[0]?.message }}
  </p>
}
```
#### Validaciones dependientes de otros campos

A nivel visual, los campos de nombre, apellidos y selección del curso solo aparecen cuando se ha seleccionado la opción de hacer un curso, por lo que las validaciones de estos campos solo se deben aplicar cuando el checkbox `hasCourse` está marcado.

```ts
required(schema.firstName, {
  when: ({ valueOf }) => valueOf(schema.hasCourse) === true,
  message: 'El nombre es obligatorio',
});
```

Podemos crear un segundo schema de validación, con aquellas que solo se aplican cuando el checkbox `hasCourse` está marcado, y que se añada al schema principal mediante la función `applyWhen()`, que nos permite añadir un schema adicional condicional.

```ts
readonly #optionalsSchema = (path: SchemaPathTree<RegisterModel>) => {
  required(path.firstName, { message: 'El nombre es obligatorio' });
  required(path.surname, { message: 'El apellido es obligatorio' });
  required(path.course.key, { message: 'El curso es obligatorio' });
};

protected readonly registerForm: FieldTree<RegisterModel> = form(this.user, (path) => {
  this.#registerFormSchema(path);
  applyWhen(
    path,
    ({ valueOf }) => valueOf(path.hasCourse) === true,
    (path) => this.#optionalsSchema(path)
  );
});
```

#### Submit y Navegación

Como en los ejemplos anteriores, de formularios con signals, aprovechamos la directiva FormRoot y la forma de gestionar el submit como unas lógica interna del propio formulario. 

```ts
protected readonly registerForm: FieldTree<RegisterModel> = form(
    //..
  {
  submission: { action: this.submitForm.bind(this) },
  },
}
```

El proceso de submit será muy similar al del formulario de login, incluyendo: 

- la llamada a un servicio, responsable del registro de cara al backend, pasándole los datos de la signal value(), esperando qa qu se resuelva la promesa.
- un reset del formulario (ahora con el método `reset(INITIAL_VALUES)` del FormGroup) para dejarlo limpio para un nuevo intento de login.
- la navegación dependiendo del resultado,  utilizando el servicio `Router` de Angular.


### Custom Controls y selección de opciones

En el formulario de registro vemos que se repiten los inputs y los checkboxes, e incluso los radio buttons y los select, tienen un templete definido con el que podría pasar lo mismo.

En todos los casos podemos crear **componentes personalizados** para cada uno de estos controles, que nos permitan reutilizarlos en otros formularios, y que nos permitan encapsular la lógica de validación y feedback de cada control. De esta forma estaremos creando un sistema de diseño (System Design) propio, que nos permitirá mantener la consistencia visual y funcional de nuestra aplicación.

#### 🧿Custom RadioButtons

Al crear un componente custom para los radiobutton siguiendo el mismo planteamiento que en casos anteriores, es fácil solucionar el problema en nuestro modelo del formulario, donde hemos definido la propiedad que usará el control de radio buttons como un objeto (`gender: Gender`), mientras que el elemento HTML nativo de tipo radio button solo devuelve el valor de la opción seleccionada, y no el objeto completo. 

Como antes, debemos crear un componente que implemente el interface `FormValueControl<T>`, donde T corresponderá al tipo de datos maestros que manejen las opciones del radio button.

En consecuencia, el componente reciba como inputs 
- el texto que debe mostrar (label), 
- un array de opciones
- el FieldState del control que representa el radio button, que es recogido por la directiva `FormField` y que nos permite acceder al valor del control, a su estado de validación y a sus errores.

```ts
@Component({
  ...
})
export class RadioButtons<T extends { key: string; message: string }> implements FormValueControl<T> {
 
  readonly value = model.required<T>();

  readonly errors = input([] as readonly ValidationError[]);
  readonly invalid: InputSignal<boolean> = input(false);
  readonly touched = model(false);

  readonly legend = input.required<string>();
  readonly options = input.required<T[]>();
  readonly id = computed<string>(() => this.#generateId());

  #generateId() {
    return `radio-${Math.random().toString(36).slice(2, 9)}`;
  }
```

El uso del tipado genérico nos permite crear un componente que pueda ser utilizado con cualquier objeto que tenga las propiedades `key` y `message`, como en nuestro caso los objetos `Gender` y `Course`.

En el template, iteramos sobre las opciones y creamos un input de tipo radio para cada una de ellas, con su correspondiente label.

Como en otros controles personalizados, usamos el binding de `[checked]` con la expresión `value().key === item.key`  y el evento `(change)` para actualizar el valor del la signalModel `value()` cuando se selecciona una opción.

```html
<fieldset>
  <legend>{{ legend() }}</legend>
  @for (item of options(); track $index) {
    <label [for]="'gender-' + item.key" class="form-control checkbox">
      <input
        type="radio"
        [id]="'radio-' + item.key"
        [checked]="value().key === item.key"
        (change)="value.set(item)"
        (blur)="touched.set(true)"
        [value]="item.key"
      />
      <span>{{ item.message | titlecase }}</span>
    </label>
  }
</fieldset>
@if (invalid() && touched()) {
  <p class="error">{{ errors()?.[0]?.message }}</p>
}
```

El componente necesita dos pequeños ajustes:

- marcarlo touched cuando se pierde el foco, para que se muestren los errores de validación cuando el usuario interactúa con el control
- mostrar los errores de validación gracias a la vinculación que hace internamente la directiva FormField, entre los inputs del componente y los estados en el FieldState, y que nos permite acceder a los errores de validación como `errors()` o 

El problema esta en que no podemos acceder a los errores de validación como `errorSummary()`, lo que implicará un cambio en la validación cuando usemos el control, como veremos en el test del componente.

#### Validaciones personalizadas

Entre las opciones ya mencionadas para testar un control personalizado, vamos a optar por añadir un componente de prueba que utilice el componente `RadioButtons`, y que nos permita tester su comportamiento en un formulario, y su integración con la directiva `FormField`.

Este enfoque, además de su sencillez, nos permite documenter la forma de uso de nuestro control personalizado, que implicará
crear un esquema de validación personalizado para el control. Así podremos comprobar que los errores de validación se muestran correctamente en el template.

```ts
interface RadioOption { key: string; message: string }

interface MockModel {
  name: { key: string; message: string };
}

@Component({
  selector: 'alc-test-host',
  imports: [RadioButtons, FormField],
  template: `
    <form>
      <alc-radio-buttons
        [legend]="'Testing radio buttons'"
        [options]="radioOptions"
        [formField]="fieldTree.name"
      />
    </form>
  `,
})
class TestHostComponent {
  mockModel = signal<MockModel>({
    name: { key: '', message: '' },
  });
  schema = (path: SchemaPathTree<MockModel>) => {
     validate(path.name, ({ value }) => {
      if (value().key === '') {
        return {
          kind: 'required',
          message: 'Name is required',
        };
      }
      return null;
    });
  };

  radioOptions: RadioOption[] = [
    { key: 'option1', message: 'Option 1' },
    { key: 'option2', message: 'Option 2' },
    { key: 'option3', message: 'Option 3' },
  ];

  fieldTree = form(this.mockModel, this.schema);
}
```
Como vemos, al preparar el componente host para el test, utilizamos un esquema diferente, con una **validación personalizada**.

- importamos `validate` desde '@angular/forms/signals';
- su segundo parámetro es la función de validación, que recibe un objeto con la propiedad `value`, que es un signal que representa el valor del control, y que nos permite acceder a su valor actual mediante `value()`;
- si el valor del control es inválido, devolvemos un objeto con la propiedad `kind` y `message`, que representa el tipo de error y el mensaje de error correspondiente;
- si el valor del control es válido, devolvemos `null`.

De esta forma, los errores de validación se almacenan en el FieldState del control, y podemos acceder a ellos mediante `errors()` en lugar de necesitar `errorSummary()`.

```ts
protected onSelectChange(target: EventTarget | null) {
```

La lógica del componente también es muy similar a la del formulario original

- creamos un objeto con los valores iniciales del formulario, que incluye los campos opcionales
- creamos un signal con el objeto del formulario, que será el que se pase al form
- definimos un esquema de validación para los campos obligatorios, y otro para los campos opcionales, que se aplicará solo cuando el checkbox `hasCourse` esté marcado

En los controles de selección multiple, como los radio buttons y el select, debemos tener en cuenta que el valor del control es un objeto, y no un string, por lo que la validación personalizada debe comprobar la propiedad `key` del objeto para determinar si el valor es válido o no.

```ts
  readonly #auth = inject(Auth);

    password: '',
    firstName: '',
    surname: '',

    isOk: false,
    hasCourse: false,
    course: { key: '', message: '' },

  protected readonly courses = signal(COURSES);

  protected readonly user = signal<RegisterModel>(this.#initialValues);

  readonly #optionalsSchema = (path: SchemaPathTree<RegisterModel>) => {
    required(path.firstName, { message: 'El nombre es obligatorio' });
    required(path.surname, { message: 'El apellido es obligatorio' });
    validate(path.course, ({ value }) => {
      if (value().key === '') {
        return {
          kind: 'required',
          message: 'El curso es obligatorio',
        };
      }
      return null;
    });
  };

  readonly #registerFormSchema = (path: SchemaPathTree<RegisterModel>) => {
    required(path.email, { message: 'El email es obligatorio' });
    email(path.email, { message: 'El email no es válido' });

    minLength(path.password, 6, { message: 'La contraseña debe tener al menos 6 caracteres' });

      if (value().key === '') {
        return {
          kind: 'required',
          message: 'Indicar el género es obligatorio',
        };
      }
      return null;
    });
    required(path.isOk, { message: 'Debes aceptar los términos y condiciones' });

    this.user,
    (schema) => {
      this.#registerFormSchema(schema);
      applyWhen(
        schema,
        ({ valueOf }) => valueOf(schema.hasCourse) === true,
        (schema) => this.#optionalsSchema(schema),
      );
    },
    {
      submission: {
        action: this.submitForm.bind(this),
      },
    },
```

## Extras (descartes)

### Custom Controls

#### 🧿Custom CheckBox-Free

Este componente es un wrapper del input nativo de tipo checkbox, que nos permite utilizarlo como un componente de Angular, y que nos permite enlazarlo con un signal de tipo boolean. Como no estamos pasando elementos de formulario, podríamos usar el componente libremente, fuera de un formulario.

El componente recibe dos inputs:

- `checked`: un signal de tipo boolean que representa el estado del checkbox
- `label`: un signal de string que representa el texto que se muestra al lado del checkbox

Y un output

- `checkedChange`: un output que emite un evento cuando el estado del checkbox cambia, para que el componente padre pueda actualizar su signal correspondiente.

```ts
export class  CheckBoxFree { {

  readonly checked = input.required<boolean>();
  readonly checkedChange = output<boolean>();
  readonly label = input.required<string>();
}
```

En el template, utilizamos un label que contiene el input de tipo checkbox, y un span que muestra el texto del label. 

El input está enlazado con el signal `checked` mediante la propiedad `[checked]`, y el evento `(checkedChange)` emite el evento `emitCheckedChange`, que corresponde al cambio de estado del checkbox, realizado a nivel visual en el HTML.

```html
<label class="custom-checkbox">
  <input type="checkbox" 
        [checked]="checked()" 
        (change)="checkedChange.emit(!checked())" />
  <span class="check-mark"></span>
  <span class="label-text">{{ label() }}</span>
</label>
```

##### Uso desde el formulario

En el formulario de registro, utilizamos el componente `CheckBoxFree` para el campo `hasCourse` y enlazamos su estado con el signal `registerForm.hasCourse()` mediante la propiedad `[checked]`, y el evento `(emitCheckedChange)` llama al método `updateHasCourse()` que actualiza el signal correspondiente.

```html
  <alc-check-box
    [label]="'Accept Terms ...'"
    [checked]="registerForm.hasCourse().value()"
    (emitCheckedChange)="updateHasCourse($event)"
  />
```

```ts
  protected updateHasCourse(newChecked: boolean) {
    this.registerForm.hasCourse().value.set( newChecked )
  }
```

#### Signal model()

En el caso anterior, en el componente `CheckBoxFree`,   podríamos utilizar otra primitiva de señales, `model()`, que nos permite agrupar en un solo elemento las dos direcciones de comunicación, input y output.

```ts
export class CheckBoxFree {
    // readonly checked = input.required<boolean>();
    // readonly checkedChange = output<boolean>();
  readonly checked = model.required<boolean>();
  
  readonly label = input.required<string>();
}
```

En el template, en lugar de utilizar las propiedades `[checked]` hace el binding con la propiedad igual que antes pero el binding del evento cambia. Ahora no tenemos acceso directo al output: cambiamos el valor de la signal de tipo model y esta emite automáticamente un evento de cambio, que podemos escuchar en el componente padre. Para ello solo hay que tener encuentra que el nombre del evento es el nombre de la propiedad con el sufijo `Change`, en este caso `checkedChange`.

```html 
<input type="checkbox" [checked]="checked()" (change)="checked.set(!checked())" />
```

En el formulario de registro, el binding es igual que antes, ya que el evento que escuchamos ya se denominaba `checkedChange`, que es el nombre de la propiedad con el sufijo `Change`.

```html
<div aria-label="Has Course">
  <alc-check-box-free
    [label]="'Haz echo algún curso con nosotros'"
    [checked]="registerForm.hasCourse().value()"
    (checkedChange)="updateHasCourse($event)"
  />
</div>
```

Por el momento no existe una directiva similar a `[(ngModel)]` para hacer el binding bidireccional con un signal de tipo model, pero es posible crearla, y de hecho ya existe un PR abierto en Angular para implementarla.

### Mejoras en los custom controls

Los componentes creados son solo ejemplos simples de controles personalizados. En la practica puede ser necesario tener en cuenta la posibilidad de otros atributos y eventos, que se pueden definir de forma específica.

Por el hecho de utilizar los interfaces `FormValueControl` y `FormCheckboxControl`, ya tenemos un API definido para los componentes, que nos permite utilizarlos de forma consistente y predecible.

En ella se incluyen todas las siguientes propiedades, que son opcionales, en caso de definirlas en el componente, recibirán directamente su valor a partir del FieldTree del control del formulario, que estamos vinculando gracias a la directiva `formField`.

- errors: InputSignal
- disabled: InputSignal
- disabledReason: InputSignal
- readonly: InputSignal
- hidden: InputSignal
- invalid: InputSignal
- pending: InputSignal
- touched: InputSignal
- dirty: InputSignal
- name: InputSignal
- required: InputSignal
- min: InputSignal
- minLength: InputSignal
- max: InputSignal
- maxLength: InputSignal
- pattern: InputSignal
- touch: OutputRef<void>

El interface incluye también los métodos 

- focus?(options?: FocusOptions): void 
- reset?(): void 


Al margen de estas, el API expuesto por los componentes podría incluir:

- tabIndex?: number
- autocomplete?: string
- indeterminate?: boolean
- ariaLabel?: string
- ariaDescribedBy?: string
- nativeAttrs?: Record<string, string | number | boolean | null | undefined>

La última propiedad `nativeAttrs` es un objeto que permite pasar cualquier atributo nativo de HTML al input nativo del control, para que el componente sea más flexible y se pueda utilizar en diferentes contextos.

Para usar esta propiedad necesitamos:

-  en el template, añadir una referencia al control nativo.
-  en el componente, definir el input que recibirá `nativeAttrs`
-  en el constructor, crear un effect vinculado a este input que invoque un método auxiliar
-  en el método, iterar sobre las propiedades del objeto `nativeAttrs` y añadirlas al control nativo mediante Renderer2 y su método `setAttribute()`
 
```html
<input type="checkbox" #nativeInput />
```

```ts
type NativeAttrs = Record<string, string | number | boolean | null | undefined>;

export class CheckBox {
  readonly #renderer = inject(Renderer2);
  readonly #nativeAttrs = input<NativeAttrs>({});
  readonly #nativeInput = viewChild.required<ElementRef<HTMLInputElement>>('nativeInput');

  #previousNativeAttrKeys = new Set<string>();

  constructor() {
    effect(() => {
      const inputEl = this.#nativeInput();
      if (!inputEl) {
        return;
      }

      this.applyNativeAttrs(inputEl.nativeElement, this.#nativeAttrs());
    });
  }

  private applyNativeAttrs(element: HTMLInputElement, attrs: NativeAttrs): void {
    const nextKeys = new Set(Object.keys(attrs));

    for (const key of this.#previousNativeAttrKeys) {
      if (!nextKeys.has(key)) {
        this.renderer.removeAttribute(element, key);
      }
    }

    for (const [key, value] of Object.entries(attrs)) {
      if (value === null || value === undefined || value === false) {
        this.renderer.removeAttribute(element, key);
        continue;
      }

      if (value === true) {
        this.renderer.setAttribute(element, key, '');
        continue;
      }

      this.renderer.setAttribute(element, key, String(value));
    }

    this.#previousNativeAttrKeys = nextKeys;
  }
}
```

Este sería un buen caso de uso de cuando crear un directiva propia en Angular, incorporando este código y evitando la necesidad de repetirlo en cada uno de los controles personalizados. 

#### 🧿Directiva NativeAttrs

Creamos la directiva

```shell
ng g d core/directives/native-attrs --project demo-03 
```

Incluimos la funcionalidad que podríamos haber añadido en los componentes

- creamos un tipo para los posibles atributos nativos, que es un objeto "Record" con claves de tipo string y valores de tipo string, number, boolean, null o undefined

```ts
export type NativeAttrRecord = Record<string, string | number | boolean | null | undefined>;
```

-  en el selector, limitamos el uso de la directiva a los controles de formulario

```ts
@Directive({
  selector: 'input[alcNativeAttrs], textarea[alcNativeAttrs], select[alcNativeAttrs]',
  // selector: '[alcNativeAttrs]',
})
```

- en la directiva, como suele ser habitual, inyectamos Renderer2 y ElementRef, que nos permiten acceder al elemento nativo del control y modificar sus atributos de forma segura y compatible con Angular.

- como input recibimos los atributos, de acuerdo con el tipo `NativeAttrRecord` definido anteriormente, y creamos un set para almacenar las claves de los atributos que se han aplicado previamente, para poder eliminarlos si ya no están presentes en el objeto de atributos.

```ts
export class NativeAttrs {
  readonly alcNativeAttrs = input<NativeAttrRecord>({});
  readonly #elementRef = inject(
    ElementRef<HTMLInputElement | HTMLTextAreaElement | HTMLSelectElement>,
  );
  readonly #renderer = inject(Renderer2);

  #previousKeys = new Set<string>();
}
```

-  en el constructor, crear un effect vinculado al input que invoque un método auxiliar

```ts
constructor() {
  effect(() => {
    this.applyAttrs(this.alcNativeAttrs());
  });
}
```

-  en el método, igual que anteriormente, podemos iterar sobre las propiedades del objeto `nativeAttrs` y añadirlas al control nativo mediante Renderer2 y su método `setAttribute()`

```ts
private applyAttrs(attrs: NativeAttrRecord): void {
  const element = this.#elementRef.nativeElement;
  const nextKeys = new Set(Object.keys(attrs));

  // Remove attributes that are no longer present
  for (const key of this.#previousKeys) {
    if (!nextKeys.has(key)) {
      this.#renderer.removeAttribute(element, key);
    }
  }

  // Add or update attributes based on the new values
  for (const [key, value] of Object.entries(attrs)) {
    if (value === null || value === undefined || value === false) {
      this.#renderer.removeAttribute(element, key);
      continue;
    }

    if (value === true) {
      this.#renderer.setAttribute(element, key, '');
      continue;
    }

    this.#renderer.setAttribute(element, key, String(value));
  }

  this.#previousKeys = nextKeys;
}
```

En el template de nuestros componentes personalizado, aplicamos la directiva al control nativo (input, textarea, select).

```html
<input 
  type="{{ type() }}" 
  id="{{ id() }}" 
  [value]="value()"
  (input)="value.set($event.target.value)"
  (blur)="touched.set(true)"
  placeholder=" " 
  [alcNativeAttrs]="nativeAttrs()"
/>
```

Y en el componente recogemos el objeto de atributos nativos como input.

```ts
export class Input {
  //...
    readonly nativeAttrs = input<NativeAttrRecord>({});
}
```

En el formulario que utiliza nuestro componente personalizado, podemos pasar cualquier atributo nativo que queramos aplicar al control nativo, como los atributos `aria-` que permiten mejorar la accesibilidad del formulario, o cualquier otro atributo que necesitemos.

```html
<alc-input
      aria-label="Email"
      [label]="'Email'"
      type="email"
      [formField]="registerForm.email()"
      [nativeAttrs]="{ 'aria-describedby': 'email-error' }"
    />
```
