## Patrón controlador (contenedor) / presentadores

Cualquier situación que incluye una lista con una serie de items es buena practica componentizarla, separando la lista y el item como componentes que se pueden comunicar tal como hemos visto.

Podríamos utilizar una lista de tareas, de notas, de cursos, de productos, de usuarios, etc.

En nuestro caso vamos a utilizar una lista de cursos, completando la feature que ya tenemos

El patrón de diseño que vamos a utilizar es el patrón controlador (contenedor) / presentadores, que consiste en separar la lógica de negocio y la lógica de presentación en componentes diferentes, que se comunican mediante inputs y outputs.

- el componente contenedor (CoursesContainer) se encarga de la lógica de negocio, y de decidir qué mostrar según la ruta, y de pasar los datos al componente presentador (CoursesList, CourseItem, CourseForm) mediante inputs
- los componentes presentadores se encargan de la lógica de presentación, y de emitir eventos al componente contenedor mediante outputs

#### 🕸️Servicio repositorio simulado

```shell
ng g s features/courses/services/courses-repo --project course-02
```

Creamos un servicio repositorio simulado para la feature de cursos, que nos permitirá obtener los cursos desde el mock de datos iniciales.

Como ya hicimos en los servicios de Auth, añadimos un parámetro de opciones que nos permite indicar el retraso en la respuesta, y el resultado como éxito o error.

En el primer caso devolvemos un observable con el mock de cursos que hemos creado previamente, con un retraso por defecto de 1 segundo para simular la respuesta de un servicio real.

En el segundo caso hacemos que el observable lance un error para simular un error en la obtención de los cursos, para poder probar el manejo de errores en los componentes que consumen el servicio.

```ts
interface ServiceOptions {
  success: boolean;
  delayTime: number;
}

const DEFAULT_SERVICE_OPTIONS: ServiceOptions = {
  success: true,
  delayTime: 1000,
};

@Service()
export class CoursesRepo {
  getAll(options: Partial<ServiceOptions> = {}): Observable<Course[]> {
    const finalOptions = { ...DEFAULT_SERVICE_OPTIONS, ...options };

    if (!finalOptions.success) {
      return throwError(() => new Error('Error al obtener los cursos'));
    }
    return of(COURSES).pipe(delay(finalOptions.delayTime as number));
  }
}
```

#### 🧿Componente CourseContainer

En la lógica del contenedor `CoursesContainer`, definimos una propiedad de tipo signal para discriminar qué mostrar.

```ts s courses-container.ts

type PageTypes = 'list' | 'add' | 'edit' | 'detail';

export class CoursesContainer {
  protected readonly pageType = signal<PageTypes>('list');
}
```

En el template del contenedor, debemos mostrar el componente correspondiente según el valor de `pageType`, utilizando un `switch` para renderizar el componente correspondiente.

```html courses-container.ts
  @let type = pageType();
  @switch (type) {
    @case ('list') {
      <alc-filter />
      <alc-course-item />
    }
    @case ('add') {
      <alc-course-form />
    }
    @case ('edit') {
      <alc-course-form />
    }
    @case ('detail') {
      <alc-course-item-pro />
    }
    @default never;
  }
```

Al utilizar un render condicional en lugar de un enrutamiento con `router-outlet`, conservamos acceso a los componentes hijos, y podemos pasarles inputs o escuchar eventos, que será la clave del patrón controlador/presentadores, que queremos aplicar en este caso.

  //...

Cada uno de los botones emite un evento con el id del curso, que será capturado por el componente contenedor `CoursesContainer`, que se encargara de gestionar las respuestas a los eventos, eliminando un curso o cambiando el valor de la señal `pageType` para mostrar el componente correspondiente.

```ts course-item.ts
export class CourseItem {
  readonly course = input.required<Course>();
  
  readonly deleteEvent = output<Course['id']>();
  readonly editEvent = output<Course['id']>();
  readonly detailEvent = output<Course['id']>();

  protected emitDeleteEvent() {
    this.deleteEvent.emit(this.course().id);
  }

  protected emitShowEditEvent() {
    this.showEditEvent.emit(this.course().id);
  }

  protected emitShowDetailEvent() {
    this.showDetailEvent.emit(this.course().id);
  }
}
```

Como componente contenedor, `CoursesContainer` es el responsable del estado correspondiente a la lista de cursos. En respuesta a los eventos procedentes de los componentes presentadores, el contenedor debe actualizar el estado y cambiar el valor de la señal `pageType` para mostrar el componente correspondiente.

#### Carga de cursos (Read)

- para obtener los datos inyectamos el servicio repositorio simulado `CoursesRepo`, que ya hemos creado

- se almacenará el estado en una serie de signals 
  - `courses`, que será un array de cursos, y que se inicializará con un array vacío
  - `loading`, que indicará si se están cargando los cursos
  - `error`, que contendrá el mensaje de error en caso de que ocurra alguno

- se obtendrán los datos mediante un método `loadCourses` que será invocado desde el constructor. 

En este se ejecuta el método getAll() del servicio para obtener un observable, al que nos subscribimos para obtener los datos, pasándole un observer con dos callbacks: 

- en el callback de next se actualiza el signal `courses` con los datos obtenidos, y se pone a false el signal `loading`. 
- en el callback de error se actualiza el signal `error` con el mensaje de error, y se pone a false el signal `loading`.

El estado final de la signal `loading` no se puede controlar en el callback de `complete`, que es distinto del finally de las promesas, y solo se ejecuta cuando el observable se completa, lo que no ocurre en caso de que se emita un error. 

Para conseguir esa funcionalidad, podemos utilizar el operador `finalize` de RxJS, que nos permite ejecutar un callback cuando el observable se completa o emite un error, y en ese callback podemos poner a false el signal `loading`. En nuestro caso, como queremos que el signal `loading` se ponga a false en ambos casos, podemos ponerlo en ambos callbacks de next y error, y no necesitamos el operador finalize.


```ts courses-container.ts
  readonly coursesRepo = inject(CoursesRepo);
  readonly #destroyRef = inject(DestroyRef);
  protected readonly courses = signal<Course[]>([]);
  protected readonly error = signal<string | null>(null);
  protected readonly loading = signal<boolean>(false);

  #loadCourses() {
    this.loading.set(true);
    this.error.set(null);
    this.coursesRepo.getAll()
    .pipe(
      takeUntilDestroyed(this.#destroyRef))
    .subscribe({
      next: (courses) => {
        this.courses.set(courses);
        this.loading.set(false)
      },
      error: (error: Error) => {
        console.error('Error loading courses:', error);
        this.courses.set([]);
        this.error.set(error.message);
        this.loading.set(false)
      },
    });
  }

    constructor() {
    this.#loadCourses();
  }
}
```

#### Cambios en el la vista

Parte de la funcionalidad de este componente es cambiar la vista que se muestra según el valor de la señal `pageType`, que se puede cambiar en respuesta a los eventos emitidos por los componentes presentadores.

Para ello, añadimos el método `changeView` que actuará como listener de los eventos emitidos por los componentes presentadores, y que cambiará el valor de la señal `pageType` según el tipo de evento recibido.

```ts courses-container.ts
protected changeView(view: PageTypes, id?: Course['id']) {
  if (id) {
    const selectedCourse = this.courses().find((course) => course.id === id) || null;
    this.currentCourse.set(selectedCourse);
    if (!selectedCourse) {
      console.warn(`Course with id ${id} not found.`);
      this.pageType.set('list'); // Revert to list view if course not found
      return
    }
  } else {
    this.currentCourse.set(null);
  }
  this.pageType.set(view);
}
```

Este método irá
 - vinculado a los eventos de los componentes presentadores
 - ejecutado directamente desde el template del componente contenedor, pasando como parámetro el tipo de vista a mostrar, y el id del curso correspondiente en caso de que sea necesario.

1. Añadir curso (botón ➕): cambia la vista a `add`, y no necesita id de curso.
   
  ```html courses-container.ts
  <button (click)="changeView('add')" title="Agregar">➕</button>
  ```

2. Eventos del componente CourseItem (presentador): cambia la vista a `edit` o `detail`, y pasa el id del curso correspondiente.

  ```html courses-container.ts
  <alc-course-item [course]="course" (editEvent)="changeView('edit', $event)" (detailEvent)="changeView('detail', $event)" />
  ```

3. Evento "cancelar" del componente CourseForm (presentador): cambia la vista a `list`, y no necesita id de curso.

  ```html courses-container.ts
   <alc-course-form (cancelEvent)="changeView('list')" />
  ```

4. Botón de volver (junto al componente CourseItemPro): cambia la vista a `list`, y no necesita id de curso.

  ```html courses-container.ts
  <alc-course-item-pro />
  <footer>
    <button (click)="changeView('list')" title="Volver">🔙</button>
  </footer>
  ```

#### Cambios en el estado (Create, Update, Delete)

Los métodos responsables del cambio de estado son en todos los casos un **update** del signal `courses`, que es el que contiene la lista de cursos, y que se actualiza con el resultado del callback correspondiente.

```ts

#generateId(): number {
  let id: number;
  while (true) {
    id = Math.floor(Math.random() * 1000000); // Genera un ID aleatorio entre 0 y 999999
    if (!this.courses().some((course) => course.id === id)) {
      break; // Salir del bucle si el ID generado no existe en la lista de cursos
    }
  }
  return id;
}

protected deleteCourse(id: Course['id']) {
  console.log('Deleting course with ID:', id);
  this.courses.update((courses) => courses.filter((course) => course.id !== id));
}

protected addCourse(course: Omit<Course, 'id'>) {
  console.log('Adding new course:', course);
  this.courses.update((courses) => [...courses, { ...course, id: this.#generateId() }]);
}

protected editCourse(id: Course['id'], course: Partial<Omit<Course, 'id'>>) {
  console.log('Editing course with ID:', id);
  console.log('New course data:', course);
  this.courses.update((courses) => courses.map((c) => (c.id === id ? { ...c, ...course, id } : c)));
}

Así podremos probar el formulario con datos ya rellenados, y no tener que rellenarlo manualmente cada vez que queramos probarlo.


#### Lógica del formulario basado en signals

Como todo formulario basado en signals, definimos un signal `courseForm` que contendrá el modelo de datos del formulario. Sin embargo en este caso queremos que su valor pueda provenir de un input (edición de un curso existente) o de un valor por defecto (añadir un curso nuevo). 

Podríamos utilizar una signal y controlar en ngOnInit, o mejor en un effect, si el input tiene valor o no, para inicializar la signal con el valor del input o con un valor por defecto. 

Sin embargo, de acuerdo con la documentación de Angular, es mejor utilizar una
`linked signal`, que se actualice automáticamente cuando cambie el valor del input. 


```ts course-form.ts
export class CourseForm {
  //readonly #courseModel = signal<CourseFormModel>(SAMPLE_COURSE);
  readonly courseToEdit = input<Course>();

  readonly #courseModel = linkedSignal<CourseFormModel>(() => {
    const course = this.courseToEdit();

    if (!course) {
      return SAMPLE_COURSE;
    }

    return {
      id: course.id,
      title: course.title,
      description: course.description,
      topic: {
        key:
          TOPICS.find((topic) => topic.message === course.topic)?.key ??
          ('' as TopicKey),
        message: course.topic,
      },
      level: {
        key: course.level[0].toLowerCase() as LevelKey,
        message: course.level,
      },
      duration: course.duration,
      image: course.image,
      courseStats: {
        difficulty: course.courseStats.difficulty.toString(),
        utility: course.courseStats.utility.toString(),
        actualization: course.courseStats.actualization.toString(),
      },
    };
  });
  ...
};
```

Como el texto del botón de enviar cambia según el modo (añadir o editar), definimos una computed signal `buttonLabel` que devuelve el texto correspondiente según el valor del input `courseToEdit`.

```ts course-form.ts
  readonly buttonLabel = computed(() => {
    this.courseToEdit() ? 'Actualizar curso' : 'Añadir curso',
  });
```

Traemos los datos maestros de los niveles y temas, para poder utilizarlos en el template del formulario.

```ts course-form.ts
  readonly levels = LEVELS;
  readonly topics = TOPICS;
```

Definimos los outputs correspondientes a los eventos de añadir/editar y cancelar, que serán emitidos por el componente presentador `CourseForm`, y capturados por el componente contenedor `CoursesContainer`.

```ts course-form.ts
  readonly formResultEvent = output<Course>();
  readonly cancelEvent = output<void>();
```

Hemos unificado en un solo caso el evento de añadir y editar, ya que ambos casos se pueden tratar de la misma forma, y el componente contenedor `CoursesContainer` puede decidir si se trata de un curso nuevo o de un curso existente, en base al id del curso, que en caso de un curso nuevo será NaN, y en caso de un curso existente será un número.

Finalmente, como ya sabemos para los formularios basados en signals, definimos es e scheme del formulario y creamos el FieldTree correspondiente, incluyendo la vinculación al método responsable del submit del formulario.

```ts course-form.ts
  readonly #courseFormSchema: SchemaOrSchemaFn<CourseFormModel> = (
    path: SchemaPathTree<CourseFormModel>,
  ) => {
    required(path.title, { message: 'El título es obligatorio' });
  };

  protected readonly courseFieldTree = form(this.#courseModel, this.#courseFormSchema, {
    submission: {

El método submitForm se encargará de emitir el evento `formResultEvent` con el valor de obtenido a partir del FieldTree del formulario, Ese evento será capturado por el componente contenedor `CoursesContainer`.

```ts course-form.ts
  async #submitForm(courseFieldTree: FieldTree<CourseFormModel>) {
    const formData: Course = {
      id: courseFieldTree.id().value(),
      title: courseFieldTree.title().value(),
      description: courseFieldTree.description().value(),
      topic: courseFieldTree.topic().value().message as Topic,
      level: courseFieldTree.level().value().message as Level,
      duration: courseFieldTree.duration().value(),
      image: courseFieldTree.image().value(),
      courseStats: {
        difficulty: parseInt(courseFieldTree.courseStats.difficulty().value(), 10),
        utility: parseInt(courseFieldTree.courseStats.utility().value(), 10),
        actualization: parseInt(courseFieldTree.courseStats.actualization().value(), 10),
      },
    };
    this.formResultEvent.emit(formData);
  }

```ts course-form.ts
  protected emitCancelEvent() {

### 🧿Uso del formulario en el Componente CoursesContainer (contenedor)

En el template del componente vinculamos los eventos del formularios con los métodos responsables de añadir o editar curso, y de cancelar.

```html courses-container.ts
  @case ('add') {
    <alc-course-form (cancelEvent)="changeView('list')" 
      (formResultEvent)="addCourse($event)" />
  }
  @case ('edit') {
    <alc-course-form
      [courseToEdit]="currentCourse() || undefined"
      (cancelEvent)="changeView('list')"
      (formResultEvent)="editCourse($event.id, $event)"
    />
  }
  ```

Completamos los métodos `addCourse` y `editCourse` para que actualicen la lista de cursos en base al evento emitido por el formulario.

```ts courses-container.ts
  protected addCourse(course: Omit<Course, 'id'>) {
    console.log('Adding new course:', course);
    this.courses.update((courses) => [...courses, { ...course, id: this.#generateId() }]);
    this.changeView('list'); // Cambia la vista a 'list' después de agregar un curso
  }

  protected editCourse(id: Course['id'], course: Partial<Omit<Course, 'id'>>) {
    console.log('Editing course with ID:', id);
    console.log('New course data:', course);
    this.courses.update((courses) =>
      courses.map((c) => (c.id === id ? { ...c, ...course, id } : c)),
    );
    this.changeView('list'); // Cambia la vista a 'list' después de editar un curso
  }
```
